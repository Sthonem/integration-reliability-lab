# How this maps to payments, APIs and customer deployments

The lab is small on purpose. Each part stands in for a problem that comes up
when software is deployed into a customer's real systems. This note links each
pattern here to the place it matters in practice, and says where the lab
simplifies.

## Payments

| In the lab | In production payments | What carries over |
|---|---|---|
| Authorise, then capture, with partial capture possible (`POST /payments`, `/capture`) | Card payments are often authorised first and captured later (tips, final amounts, split shipments). Partial approvals and partial captures happen. | The order's money state is derived from **all** of its payments (`authorized_minor`, `captured_minor`), not from the last event. `partially_paid` and `overpaid` are statuses the system has to support. |
| Integer minor units plus a currency (`19000` TRY) | The same rule everywhere money is stored or sent | Floating-point amounts are rejected at the schema level. Totals come from the POS menu, never from the client. |
| `Idempotency-Key`: the same key and body replays the stored response, the same key with a different body gets 422, a key still in flight gets 409, and only 2xx responses are cached | This is how idempotency keys work in most payment APIs | The **stable key per business action** (`loyalty-accrual:<order>`) is what makes retries safe. The timeout scenario measured it: 50 timed-out calls, **0** double credits with a stable key, **50/50** double credits with a fresh key per retry. |
| A charge taken twice is reported as `overpayment` | Duplicate charges from terminal or client retries, typically found days later at settlement | Reconciliation against the provider's own records finds them within one run. The refund stays a human decision. |
| Reconciliation against the provider's REST API | Settlement and payout reports, dispute files, and the provider's list endpoints | The same comparison runs in a loop: provider record against our record, with typed mismatches, a grace period, and "already in our inbox" skipping. A production version would also read settlement files. |

## APIs and webhooks

| Pattern | Why it exists |
|---|---|
| HMAC-SHA256 over `id.timestamp.raw_body`, timestamp tolerance, constant-time compare, several valid secrets during rotation (Standard Webhooks headers) | Webhook endpoints are public. Without a timestamp inside the MAC, a captured request could be replayed forever. Without rotation, changing a secret means downtime. |
| Verify the raw bytes before parsing, and never store unauthenticated bodies | Re-serialising JSON breaks signatures. Storing forged bodies makes it possible to plant data in the system. |
| 2xx for duplicates, 409 or 503 with `Retry-After` for "try later", 4xx for "never" | Providers retry anything that is not 2xx. The status code tells the sender what to do next. |
| Inbox with `UNIQUE(source, event_id)`, and Redis only as a fast path | Exactly-once delivery is not available, so the effect has to be exactly-once instead. Correctness must not depend on a cache. |
| A per-resource `sequence`, with park-and-resume and a timeout to the DLQ | Providers do not guarantee ordering. Webhooks for different resources (payment before order) arrive in any order, too. |
| Transactional outbox with retries, exponential backoff with full jitter, and a deadline per attempt | The state change and the intent to call out are committed together. No database transaction is held open over the network. |
| DLQ, replay and discard with an audit trail | Some failures need a person, such as a deleted member record. The fix is to correct the data and then replay, with a record of who did what. |
| Reconciliation with automatic backfill | Webhooks are notifications, not a ledger. The provider's API is the source of truth for its own data. |

## Customer deployments

What changes when this runs inside a customer's environment rather than a lab:

- **Secrets.** Here they are in `.env`, generated by `irlab.devtools init-env`
  and never hardcoded. At a customer site they go in a secret store (Vault, a
  cloud KMS or secrets manager). Webhook secrets are rotated with the dual-secret
  window shown here, and `OPS_API_KEY` is replaced by SSO.
- **Network.** The provider endpoints (`*_API_URL`) and the webhook ingress are
  configuration. Customers usually need allowlisted egress IPs, a WAF in front
  of `/webhooks/*`, and sometimes a VPN or private link to on-premise POS
  servers.
- **Rollout.** The first step is report-only reconciliation
  (`RECONCILE_AUTO_REPAIR=false`) on real traffic. This measures how far the
  systems already disagree before anything writes. After that, auto-repair is
  turned on, and the outbox is started with a small retry budget.
- **Operations hand-over.** The runbook ([runbook.md](runbook.md)), the
  dashboard, and alerts sent to the customer's on-call tool
  (`ALERT_WEBHOOK_URL`) are what the customer's team keeps after the engineers
  leave. The triage endpoint gives them a first read of any failure, and it is
  read-only by design.
- **Observability.** JSON logs carry a correlation id from webhook to inbox to
  order to outbox to provider (`X-Correlation-ID`), so a log query can follow
  one order across systems.
- **Data.** The only personal data the hub stores is a loyalty member id. Phone
  numbers and emails stay at the loyalty provider. Payment data is limited to
  ids, amounts and statuses; card data never reaches the hub.
- **Scale.** Claims are compare-and-set with leases, and on PostgreSQL every
  event for one order is serialised with an advisory lock. Running more worker
  replicas therefore needs no new design, though it has not been load-tested
  here.

## Where the lab simplifies

- The mocks are in-memory and well-behaved, apart from the faults injected on
  purpose. Real providers return paginated, rate-limited lists, have API
  versions, and send events with richer schemas.
- Reconciliation reads at most 1,000 records per provider per run, filtered by
  creation time. A production version would page through results with cursors
  and use settlement files for money.
- There are no refunds, reversals or voids. The hub flags them (`overpayment`,
  `points_on_unpaid_order`) and a person resolves them.
- One currency, one region, one tenant.
